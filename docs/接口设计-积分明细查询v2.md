## 1. 需求背景

现有积分明细接口只能按时间区间查询，不支持业务类型筛选，前端需自行过滤；且无缓存，大用户量下 DB QPS 偏高。v2 目标：

1. 支持按 `bizType` 筛选、按时间区间查询、分页返回；
2. 接口 P99 从约 340ms 降到 120ms 以内；
3. 为后续「积分账单导出」「积分趋势图」提供可复用的查询能力。

**范围之外**：积分发放/扣减逻辑、积分账户余额计算、历史数据迁移。

## 2. 接口定义

```java
public interface PointDetailService {
    Result<PageResult<PointDetailDTO>> pageQuery(PointDetailQuery query);
}
```

### 2.1 请求参数

| 字段 | 类型 | 必填 | 默认 | 约束 |
|---|---|---|---|---|
| pageNo | Integer | 否 | 1 | ≥ 1，超出总页数返回参数错误 |
| pageSize | Integer | 否 | 20 | 1~50，超过 50 按 50 处理 |
| bizType | Integer | 否 | - | 空=全部；取值 1消费 2签到 3退款 4活动 |
| startTime | Date | 否 | 近 90 天 | 与 endTime 跨度 ≤ 365 天 |
| endTime | Date | 否 | 当前时间 | 不得早于 startTime |

> **userId 不在请求参数中**。用户身份一律从登录态获取，入参若携带 userId 一律忽略并记录告警日志。

### 2.2 返回结构

```json
{
  "success": true,
  "data": {
    "list": [
      {
        "id": 1024,
        "bizType": 1,
        "bizTypeDesc": "消费",
        "changeAmount": -100,
        "balance": 2350,
        "remark": "订单 202611090001",
        "gmtCreate": "2026-11-09 10:12:33"
      }
    ],
    "total": 137,
    "pageNo": 1,
    "pageSize": 20
  }
}
```

### 2.3 错误码

| code | 含义 | 触发场景 |
|---|---|---|
| 40001 | 参数错误 | 时间跨度超 365 天、startTime > endTime |
| 40002 | 页码越界 | pageNo > 总页数 |
| 40301 | 无权限 | 未登录 / 身份校验失败 |
| 50001 | 系统繁忙 | 依赖超时，已降级仍失败 |

## 3. 表结构

```sql
CREATE TABLE `point_detail` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id`       BIGINT UNSIGNED NOT NULL                COMMENT '用户ID',
  `biz_type`      TINYINT UNSIGNED NOT NULL DEFAULT 0     COMMENT '业务类型 1消费 2签到 3退款 4活动',
  `change_amount` INT NOT NULL                            COMMENT '变动积分，正加负减',
  `balance`       INT NOT NULL                            COMMENT '变动后余额',
  `biz_no`        VARCHAR(64) NOT NULL DEFAULT ''         COMMENT '业务单号，幂等键',
  `remark`        VARCHAR(128) NOT NULL DEFAULT ''        COMMENT '备注',
  `gmt_create`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `gmt_modified`  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz` (`biz_no`, `biz_type`),
  KEY `idx_user_time` (`user_id`, `gmt_create`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='积分明细表';
```

**索引说明**：查询恒定带 `user_id`，且按 `gmt_create` 倒序，故建联合索引 `(user_id, gmt_create)`，可同时满足过滤与排序，避免 filesort。`biz_type` 选择性低，不放入索引，作为回表后过滤条件。

## 4. 缓存设计

| Key | TTL | 说明 |
|---|---|---|
| `point:detail:{userId}:{bizType}:{start}:{end}:{pageNo}:{pageSize}` | 300s ± 10% | 仅缓存 pageNo ≤ 3 |
| `point:detail:empty:{userId}:{hash}` | 60s | 空结果缓存，防穿透 |

- **只读数据**：明细写入方为积分变动服务，已与产品确认允许 5 分钟延迟，故不做写后删缓存，靠 TTL 收敛。
- **缓存故障降级**：读写缓存异常均 catch 后走 DB，不阻断主流程。
- **深分页不缓存**：pageNo > 3 时 key 数量爆炸且命中率极低。

## 5. 性能目标

| 指标 | 目标 |
|---|---|
| P99 RT | ≤ 120ms（200 QPS 压测） |
| 错误率 | < 0.01% |
| 缓存命中率 | ≥ 60% |
| 慢 SQL（>100ms） | 0 条 |

## 6. 风险与待确认

| # | 风险 | 处理 |
|---|---|---|
| 1 | 单用户明细超 10 万条时深分页变慢 | 若 explain 扫描行数 > 5000，改游标分页 + 限制最大页码 |
| 2 | 明细表数据量增长快 | 评估按 `user_id` 哈希分表，本期不做，预留 `biz_no` 全局唯一 |
| 3 | 缓存与 DB 延迟被业务方质疑 | 与产品书面确认可接受延迟时长，写入文档 |

## 7. 上线计划

灰度 1% → 10% → 50% → 100%，每级观察 ≥ 15 分钟；Diamond 开关 `point.detail.v2.enable` 控制分流，关即回到老逻辑。
